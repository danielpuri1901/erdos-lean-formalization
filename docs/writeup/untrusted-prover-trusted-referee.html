Untrusted prover, trusted referee: kernel-checked proofs from Claude Code agents, judged in GitHub Actions

by Daniel Puri3 October 2026Lean 4, Claude Code, GitHub Actions

Claude agents running in Claude Code cloud sessions produced Lean 4 proofs of two known results. A separate referee repository, which no agent can see or edit, accepted every finished run. The main result is a kernel-verified computer search result for a Green problem: for every N from 3 to 60, the N by N grid holds 2N points with no three on a line.

The proofs were the easy part. Each agent needed 10 to 15 minutes. Building a referee that a determined agent cannot fool took most of two days, and the attacks we ran against it found four holes in our own design. This post covers how the referee works, what broke, and what the numbers say.

The problem: an agent that grades itself

Lean is a programming language for proofs. You write a proof like code, and a small trusted program, the kernel, checks every step. Google DeepMind's formal-conjectures library states hundreds of math problems in Lean. Many of the proofs are a hole, written sorry.

An agent that checks its own work has easy ways to look successful. It can leave a sorry. It can add an axiom, which is an assumption it never proved. It can use native_decide, which trusts compiled code instead of the kernel. It can quietly change the statement, or redefine a word the statement uses. None of this needs bad intent. A model rewarded for "the build is green" can find these paths.

So we set one rule: nothing the agent says counts. The only definition of success is a green commit status named comparator/<target>, written by a repository the agent never sees.

Solution overview

The system has two repositories. The agent repository is attached to Claude Code cloud sessions, so the agent can change anything in it, and we trust nothing in it. The checker repository holds the frozen statements and a GitHub Actions workflow. It is never attached to a session.

When the agent wants a verdict, it pushes a commit whose message starts with submit(<target>):. A poller in the checker repository finds that commit, rebuilds it, and runs Comparator, a tool from the Lean FRO that compares a solution against a challenge statement. Comparator runs the build inside landrun, a Linux sandbox. The checker then writes a commit status back to the agent repository: green, or red with Comparator's last line as the reason.

Walkthrough

Step 1: freeze everything the agent could change

Comparator's README lists its trust assumptions. The build configuration must be trusted, and the solution must never have been compiled outside the sandbox. Our first workflow broke both. It built Solution outside landrun, and it used the agent's own lakefile.toml, which can run code at build time. It also left a token that can write commit statuses in the checkout's git config, where agent code could read it.

The fixed workflow replaces every file that steers the build with the checker's own copy, deletes anything prebuilt, and builds only the trusted statement outside the sandbox:

- name: Freeze the challenge and the build configuration
  run: |
    cp "challenge/$TARGET.lean" agent/Challenge.lean
    cp frozen/lakefile.toml frozen/lake-manifest.json frozen/lean-toolchain agent/
    rm -rf agent/lakefile.lean agent/.lake agent/.claude agent/scripts/hooks

The agent checkout also uses persist-credentials: false, and Docker is stopped before Comparator runs, because Comparator's README warns that landrun does not block Unix sockets on current Linux kernels.

Step 2: attack the referee before trusting it

Before any agent ran, we planted cheating solutions against a trivial statement. A correct proof had to pass, and each cheat had to fail for its own reason.

The last row was a real hole. Our workflow decided the verdict by searching the log for Comparator's success line. But the log also contains the solution's own build output, and a Lean file can print anything. A solution that proved True and printed the line got a green status. Now the verdict comes from Comparator's exit code plus an exact match on its last line, and this attack is a permanent test case:

set -o pipefail
bash scripts/check.sh "comparator/$TARGET.json" 2>&1 | tee comparator.log
[ "$(tail -n 1 comparator.log)" = "Your solution is okay!" ]

Step 3: a cloud environment that starts in two minutes

Each cloud session needs Lean 4.33.1 and the compiled Mathlib and formal-conjectures libraries: 7.8 GB on disk, 2.55 GB compressed. Building them takes about 10 minutes. The environment's setup script is cached only if it finishes in about five. So we build the libraries once in GitHub Actions and publish them as release assets in a public repository that holds only open-source compiled code. The setup script downloads and unpacks them in 111 seconds.

Three bugs stood between us and that number. Each one was invisible on GitHub's own runners, so we made a smoke-test workflow that copies the cloud's conditions more closely each time it missed something.

  • The setup body ran as ( set -e ... ) || echo. Bash ignores set -e inside a command whose status || tests, so a failed download never stopped the script.
  • The cloud image has no zstd command. GitHub runners have one.
  • Unpacking as root kept the archive's file owner, the CI user. The cloud session runs as root, git refuses repositories owned by another user, and Lake read that refusal as "URL has changed". It then deleted every package and started compiling Mathlib from source. That cost one session 18 minutes before we caught it.

Step 4: a feedback loop with no human in it

The orchestrator, a Claude Opus 5.5 session, reads a task list and a ledger. It sends one fresh worker per attempt with a 25-minute time box. A worker starts with lake build, which shows every error the last worker left. When it stops, it commits its state even if the build is red, so nothing is lost and nobody has to relay error messages.

After a failed attempt, the orchestrator labels it lean (a hard or unfinished proof) or math (the plan itself is wrong). We took this split from the Magenta paper's error attribution (arXiv 2609.11319). A lean failure sends a fresh worker with the same plan. A math failure makes the orchestrator rewrite the plan first. The ledger records what each attempt tried and why it failed, so the next worker does not repeat it.

Two infrastructure facts shaped this loop. Cloud sessions push to their own branches, so the poller scans every run/* and claude/* branch. And GitHub's scheduled trigger never fired in the first two hours, so the session that ran the experiment also starts the poller whenever a submission has no verdict.

The experiment

We ran a warm-up and then the main target.

Warm-up: Erdős problem 105, variant sub_four

The question: take two disjoint finite sets A and B in the plane, with A four points larger than B and not all on one line. Must some line through two points of A miss B? A forum user, Xichuan, found ten points A and six points B where every one of the 45 lines through two points of A hits B, so the answer is no. formal-conjectures still lists this variant as open at the commit we pinned. The agent formalized the counterexample, and the referee accepted it on the first attempt. The worker needed about four minutes.

Main target: Green's open problem 72 for 3 ≤ N ≤ 60

The upper bound of 2N points was already proved in formal-conjectures. The missing half is one explicit witness per N. We took the witnesses from Flammenkamp's no-three-in-line database and Prellberg's published table (MIT licence), and checked all 58 again with exact integer arithmetic. The Lean kernel checks the largest one, N = 60, in 48 seconds with decide +kernel, which adds no axiom.

We compared two arms, both on Claude Opus 5.5 at the same effort. Arm B is the full harness: orchestrator, workers, ledger, guard hook and a five-step lemma outline. Arm A is a bare session with a plain prompt and none of that. Both get the same witness data and the same referee. Runs go one at a time, so the cloud credit meter shows each run's cost.

What we learned

The target was easier than the harness

We planned for hours of proving. The agents needed 10 to 15 minutes. The reason is that the hard parts were done before any agent started: verified witness data, a Lean data file, and a timing test that showed the kernel can do the work. What was left was one bridge lemma (if the integer cross-product test passes, the real points are not collinear) and some glue. That is a short job for Opus 5.5.

On this target the bare arm was faster and cheaper. Both bare runs ignored the collinearity checker we supplied, wrote a faster one of their own (N = 60 in 11 to 17 seconds instead of 55 to 76), and passed on the first submission. The harness runs followed our outline and our checker, and that path uses more memory.

The feedback loop did its job when the infrastructure failed

Run b2's first proof built in its session, but the checker's runner was shut down after 36 minutes, almost certainly out of memory. Because the runner died, it never wrote a verdict. The status stayed "pending", and the poller skips commits that already have a status. Nobody would ever have told the agent.

We changed the poller: a pending status whose checker run has already finished now becomes a failure with the reason "checker run ended without a verdict (runner shut down, often out of memory)". From there the loop worked as designed. The orchestrator measured peak memory itself (2.1 GB at N = 40, 5.8 GB at N = 60), labelled the failure lean, and briefed a second worker to split each check into chunks. The second submission passed. Run b3 is on the same path as this post goes out.

Smaller lessons

  • A smoke test is only as good as its copy of production. Ours passed three times while the real cloud failed, because GitHub runners have zstd, run builds as a non-root user, and mark every directory safe for git.
  • Scheduled GitHub workflows are best effort. Do not build a loop on them alone.
  • Plan limits are separate from the cloud credit. Our Fable 5.1 weekly limit was used up, so every orchestrator ran on Opus 5.5 instead.

What this does not show

  • Three runs per arm is a demonstration, not a statistic.
  • The witness data and, for arm B, the lemma outline were prepared before the runs. The agents formalized; they did not search.
  • Workers ran at default effort, because the session could not pin a subagent's effort level.
  • The statement audit for Erdős 105 was written by Claude. I still have to read the Lean statement against the English problem myself before this result goes anywhere public.

The next step is a known result whose proof is conceptual rather than computational, so that planning and the failure loop have real work to do.

Who did what

I set the goal, approved the design, and made the calls that needed a human, such as publishing the dependency repository and letting the runs launch on their own. I did not write any proof or harness code. A local Claude Code session on Claude Opus 5.5 built the harness, the checker and the cloud environment, fixed the bugs above, and started each cloud session through the browser. The cloud sessions, also Claude Opus 5.5, wrote every Lean proof. An earlier session on Claude Fable 5.1 wrote the design and the plan with me.

Borrowed work: the statements come from formal-conjectures, the referee is Comparator, the sandbox is landrun, the workflow started from the nick-kuhn/erdos-619 checker, the Erdős 105 counterexample is Xichuan's, the Green 72 witnesses are Flammenkamp's and Prellberg's, and the lean-or-math failure split comes from Magenta.

Conclusion

If you let an agent work alone, put the verdict somewhere it cannot reach. Freeze every input that steers the build. Take the verdict from the tool's exit code, never from text the agent can print. And make sure a crashed check still produces an answer, because silence looks exactly like "still running". With those pieces in place, the agents did the formalization in minutes, and the referee is the part I trust.
